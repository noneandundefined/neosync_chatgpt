# Применение массовой конфигурации

Обработчики HELLO, SYNC и CONFIGURATION передают полученный хеш в
`CompanyTaskUseCase.ObserveDeviceConfiguration`. Цель задачи — её `cfg_data`;
хеш читается через существующий `common.GetCfgHash`, без отдельной копии в БД.
CONFIGURATION используется как ответ с текущей конфигурацией устройства,
аналогично существующему подтверждению `cfg_sync_status` в его обработчике.

## Состояния

- `pending`: ожидание подключения; после отключения сохраняется срок предыдущего ожидания.
- `queued`: ожидается разрешённое время повторной отправки.
- `sending`: попытка закреплена за обработчиком через `attempt_token` и `lease_until`.
- `awaiting_confirmation`: SET_CFG записан в соединение, ожидается нужный хеш.
- `completed`: устройство сообщило хеш конфигурации задачи.
- `failed`: неверная конфигурация, нет владельца либо исчерпаны попытки.
- `expired`: закончился TTL кампании.
- `cancelled`: задача отменена или заменена.

Нулевой или старый хеш не завершает задачу ошибкой. HELLO/SYNC/CONFIGURATION
с нужным хешем завершают активную задачу до истечения TTL, в том числе до
первой отправки. Конечные состояния не меняются входящими пакетами.

В диаграмме `queued`, `sending` и `awaiting_confirmation` объединены в
«Применяется». В списке устройств показан точный этап. HTTP и клиент не
вычисляют отдельный статус истечения по своим часам.

## Отправка и сроки

Настройки находятся в `tcp-server/config/config.go`:

| Настройка | Значение |
|---|---|
| `CompanyTaskConfirmationTimeout` | 2 минуты |
| `CompanyTaskRetryDelay` | 30 секунд |
| `CompanyTaskMaxAttempts` | 3 |
| `CompanyTaskLeaseTimeout` | 1 минута |
| `CompanyTaskPollInterval` | 10 секунд |
| `CompanyTaskWorkers` | 8 |

Сроки рассчитываются по времени PostgreSQL. Каждая закреплённая попытка
увеличивает `attempts`. Ошибка записи не устанавливает `last_sent_at` и
не запускает ожидание подтверждения. Повторы не продлевают `expires_at`.
Ручной повтор ошибочных задач сбрасывает счётчик попыток и параметры
доставки, но возможен только до прежнего `expires_at`.

Проверка сроков и отправка работают в отдельных фоновых циклах: медленная
запись одному устройству не блокирует обработку TTL. При перезапуске
незавершённая отправка восстанавливается после `lease_until`.

Переход проверяет статус и `updated_at` прочитанной задачи. Изменение задачи,
целевой конфигурации и пересчёт кампании выполняются в одной транзакции.
Отмена и повтор HTTP используют ту же блокировку строки кампании.
Обработчики конфигурации одной TCP-сессии сериализованы. Пока массовая
задача активна, обычная синхронизация не отправляет другую конфигурацию,
а отдельный запрос SET_CFG через RabbitMQ возвращает ошибку занятости.

Отмена не откатывает пакет, уже записанный в соединение. Конфигурация
с неправильным хешем, пришедшая во время активной задачи, не заменяет её цель.

## Обновление

Остановить старый TCP-сервер и обработку массовых задач на HTTP, применить
миграцию `20260913120000_add_company_task_delivery.sql`, затем запустить
обновлённые HTTP/TCP и клиент. Смешанная работа старой и новой версии
обработчиков статусов не поддерживается.

Миграция даёт существующим `running` две минуты на подтверждение и
преобразует просроченные активные задачи и ошибки `campaign expired`
в `expired`. Состояние кампаний пересчитывается.

## Проверки

Интеграционные тесты используют отдельные временные схемы в тестовом
PostgreSQL. Указать его URL в `NEOSYNC_TEST_DATABASE_URL` и выполнить:

```text
cd tcp-server
go test ./...

cd ../http-server
go test ./infra/store/postgres/store ./handler/v1/company_handler_v1
```

Без `NEOSYNC_TEST_DATABASE_URL` интеграционные тесты пропускаются.
Проверяются миграция вверх/вниз, старый и нужный хеши, ошибка отправки,
повторы, лимит попыток, отключение, TTL без пакетов, восстановление после
прерванной отправки, конкурирующие попытки, отмена и статистика API.
